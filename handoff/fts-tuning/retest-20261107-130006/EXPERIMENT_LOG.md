# 推送与性能释放复测

- 2026-11-07 用户批准推送测试，随后确认已切到最高性能并空闲。该设置为用户确认，Windows 平衡方案名称不能证明厂商性能档。
- 仅发布既有产品 194150497 和历史证据。新产品实验 0，累计 1/8。
- 一次有界同版窗口：最多两对、四次，官方参数和 SQL 不变。服务端 4 核、客户端 1 核，内存预算 2G；复用封存二进制，不构建。
- 使用一个全新自有数据目录；每次正常 SIGUSR1 退出后复用，旧数据与证据不动。客户端 tails 保留 1000 样本/项。
- 预登记：9 项指标每对绝对差 <=1%，SELECT1 <=2%，RSS <=2%；尾延迟 P95 <=5%、P99 <=10%。宿主负载前后 <=15%。不放宽旧噪声门槛。
- 准备阶段首次 SSH 文本解码遇到 PowerShell GBK 输出导致 UnicodeDecodeError，改为 UTF-8/GB18030 解码；没有数据库任务。另一次本地辅助文件校验误填了 hash，断言在复制前终止，随后使用已核实的 f822dddd... 正确值。均属驱动准备错误，无产品修改。
- GitHub 连接器创建 PR 返回 403（集成权限不足），使用已有 gh CLI 继续；无认证配置修改。

- 首次窗口保留一份完整参考报告（hits 全对，正常 SIGUSR1 退出），第二次开跑前 LoadPercentage=20%，触发 15% 门槛。首次 benchmark 后为11%，收尾后8%，稍后静态诊断9%；不能据此认定20%来自外部任务。
- 唯一有界续跑：保留首轮全部数据，最多再运行三次；各次开跑前固定空闲5秒，再检查同一15%门槛。没有按读数自适应等待、没有挑选样本、没有提高阈值；再次失败即停止该窗口。Microsoft Win32_Processor 文档说明 LoadPercentage 是最近一秒平均值：https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-processor 。这支持排查采样时序，不能证明本次20%的根因。

- 首两对完成，最高性能声明下仍未通过校准。随后用户明确允许必要时多跑几组；预登记唯一扩展为最多再加两对，总上限四对/八份报告。仍使用固定5秒空闲及原门槛，目的为估计波动结构，不通过平均抹去前两对失败。追加窗口另建一个自有数据目录，隔离中间正确性回归可能改变的 SQL 状态；新增磁盘约2.2GiB，保留旧目录。
