这是一个长期无人值守的自主性能优化任务。

你必须独立完成：

性能诊断 → 假设生成 → 代码修改 → 编译 → 正确性验证 → Benchmark → 性能分析 → 保留或回滚 → 下一轮探索。

你的目标是持续提高当前 FTS 最佳实现的真实性能，而不是只完成一份研究报告。

# 4. 第二阶段：性能基线校准

本阶段必须自动完成，不得要求用户批准。

## 4.1 A/A 校准

使用当前最佳二进制进行相同版本的交替测量。

判断：

- 环境噪声。
- 执行顺序影响。
- 冷热缓存差异。
- 测量方差。
- 控制项波动。

如果噪声过大，先调整实验协议。

## 4.2 A/B 测量

当前正式比较：

BEST_VALIDATED vs EXPERIMENTAL

保留所有原始样本。

保持：

- 相同数据。
- 相同参数。
- 相同构建配置。
- 相同机器环境。
- 平衡执行顺序。
- 一致的缓存预热规则。

不得修改官方 benchmark、SQL、数据量和金样。

现有六对 A/B 结果作为历史证据，不得覆盖。

# 5. 第三阶段：自主研究方向

根据真实 Profiling 结果动态选择研究方向。

初始研究队列如下。

## P0：构建、分词和 RSS

调查：

- build_ik_content 退化。
- build_beng_en 退化。
- tokenize_beng 退化。
- RSS 增长。

检查：

- allocator。
- Arena 生命周期。
- parser 初始化。
- 字典访问。
- HashMap。
- 数据拷贝。
- 字符串处理。
- CPU cache。
- 内存碎片。

不能根据函数调用次数直接判断瓶颈。

## P1：v2 分词组合

研究历史分词优化：

- 字典读锁和原子状态。
- 停用词短路。
- set_or_update。
- 等价词拼写保留。

这些修改尚未全部进入当前 v4。

先进行补丁分析，再通过独立实验决定是否值得移植。

禁止直接批量 cherry-pick。

## P2：H3 长查询内存

重点调查：

- tokens × batch 的内存增长。
- DaaT 中间结构。
- doc aggregation。
- 动态数组分配。
- 临时结构物化。
- 查询结果合并。

尝试降低内存开销，同时保留查询结果和评分语义。

## P3：查询热路径

在现有 H2/H7 优化基础上研究：

- 结果物化。
- 内存局部性。
- 固定长度比较。
- 间接函数调用。
- 数据访问模式。
- 热循环分支。

不得简单重复已验证的 H2/H7 优化。

## P4：其他跨层机会

如果 Profiling 发现新的瓶颈，可以自主扩大研究方向。

但必须保持 Issue 6 的允许修改范围和既有接口契约。

# 7. 自动晋升和回滚

## PASS

必须满足：

- 相关正确性测试通过。
- 无新增未解释回归。
- 性能提升可重复。
- 无明显 P95/P99 退化。
- 内存没有不可接受的增长。
- 测试环境可信。

保留优化，创建独立 commit。

更新 BEST_VALIDATED。

## PARTIAL

性能有改善，但验证不完整。

保留在实验分支。

不要晋升。

继续寻找补充验证。

## FAIL

性能没有改善、出现明显退化或正确性问题。

只撤销当前实验。

保留所有之前的最佳成果。

记录失败原因。

不得重复已经证明无效的实验，除非出现新的证据。

# 8. 长时间无人值守规则

本任务允许持续运行。

不需要每次修改后向用户请求确认。

不需要每完成一个阶段就暂停。

当一个方向完成后，自动选择下一个最有价值的研究方向。

如果某个方向暂时没有优化空间：

- 重新分析 Profiling。
- 检查其他调用路径。
- 检查跨层开销。
- 评估历史实验。
- 继续研究其他候选。

不得为了增加实验数量而进行无意义修改。

## 资源管理

- 不同时运行多个大型 benchmark。
- 不删除已有数据。
- 不覆盖原始证据。
- 不随意升级依赖。
- 不修改系统环境。
- 不让实验无限制消耗磁盘。
- 不让多个实验互相污染缓存和性能数据。

## 安全停止条件

只有以下情况允许主动停止：

1. 工作区数据完整性无法保障。
2. Git 状态存在无法安全隔离的冲突。
3. 测试环境发生无法恢复的故障。
4. 磁盘、内存或其他资源不足以安全继续。
5. 已经没有任何可验证的优化方向。
6. 达到预先设置的任务运行上限。

普通编译失败、单个测试失败、某次 benchmark 退化，不是停止整个任务的理由。

这些情况应当记录、回滚本轮并继续其他研究。
